# 24/7 Kiosk Survival Design

**Status:** approved for implementation planning
**Date:** 2026-10-08
**Sub-project:** A of 4 (B: Shifts, C: Trust, D: Printable timesheet follow separately)

## Intent

VardiaShift runs on a computer that stays on around the clock. Today an idle
auto sign-out drops the PC to the login screen and stops all attendance
taking until someone signs back in. After this change, the end of an admin
session changes nothing for employees: the kiosk keeps scanning and the phone
service keeps serving.

What was said: fix the 24/7 flaw, then do Phases 2, 3 and 4, adding a new
subsystem if needed. Assumptions: the PC is a shared or dedicated machine
where employees clock in without an admin present; admin functions must stay
locked behind sign-in. The service-host approach was chosen over
phone-only survival and over kiosk-suppresses-timeout.

## Constraints

These come from the project brief and are not negotiable here:

- Offline first. Anything using the network stays optional, off by default,
  silent on failure.
- Sensible defaults. A new user never touches this. No required first-launch step.
- No cloud accounts, payroll, biometrics, telemetry, or phoning home.
- Additive database migrations only. This design needs none.
- Existing security holds: parameterised SQL, audit log for admin actions,
  no secrets in logs.
- Every behaviour gets tests. UI tests close their windows in teardown.
- Windows and Linux both build. Platform-sensitive code gets a simulating test
  and a "Not verified on Windows" note.

## Root cause

Verified in code, not assumed. `MainWindow._force_logout` closes the kiosk
and the window, and `MainWindow.closeEvent` stops the phone service. Both run
on idle auto sign-out. The attendance-taking services are children of the
admin window, so they die with the admin session. The kiosk already has an
admin-password exit gate (`attendance_kiosk.py`), so keeping it alive across
logout introduces no new exposure.

## Architecture

Kiosk and phone lifetime moves from `MainWindow` to the `Application`
controller in `app/main.py`. The admin window becomes disposable: logout
destroys it and nothing else. The login window gains a way to open the
kiosk with no session. The idle timer stays in `MainWindow`, which is now
exactly right: with no admin window open there is nothing to time out.

## Components

1. **Application owns the kiosk** (`app/main.py`). `open_kiosk`,
   `_close_kiosk_silently` and the `finished` handler move from `MainWindow`.
   One kiosk instance at a time; opening it while open raises the existing one.
   The `finished` signal returns to whatever is showing (login or admin
   window) and never touches services.
2. **Phone survives the admin window** (`app/ui/main_window.py`,
   `app/main.py`). `closeEvent` keeps geometry saving and drops the
   `phone.stop()` call. `Application.shutdown` stops the phone and closes the
   kiosk together. Settings save still stops the phone when the feature is
   disabled.
3. **Login opens the kiosk** (`app/ui/login_window.py`). A Kiosk button emits
   a signal the `Application` handles. No session is created. The existing
   exit gate (admin password, audited, counts toward lockout) is unchanged,
   and a successful exit returns to the login screen, never into the admin UI.
4. **Idle timeout unchanged** (`app/ui/main_window.py`). It can only fire
   while the admin window exists. Auto sign-out closes the admin window; the
   kiosk keeps scanning and the phone keeps serving.

## Logout and quit semantics

- Manual logout, kiosk closed: admin window closes, login shows. Phone keeps
  running. Kiosk can be reopened from login.
- Manual logout, kiosk open: kiosk stays open and keeps accepting scans.
- Idle timeout, kiosk open or closed: same as manual logout. This is the flaw
  being fixed.
- Real quit (window close on login screen, OS shutdown): `shutdown` stops the
  phone and closes the kiosk. Behaviour-preserving for quit.
- First launch: setup, login, main window, identical to today. The login Kiosk
  button is extra, not required.

## Error handling

No new failure modes. Phone start failure keeps today's message. Kiosk with no
employees keeps today's empty behaviour. Opening the kiosk twice focuses the
running one instead of a second instance.

## Testing

New file `tests/test_kiosk_247.py`, one behaviour per test:

- logout keeps the phone service running (it was stopped before)
- logout keeps an open kiosk accepting scans (it was force-closed before)
- idle timeout with the kiosk open keeps scanning
- kiosk opened from login with no session accepts scans
- exit gate still demands the admin password and audits the exit
- opening the kiosk twice yields one window
- real quit stops the phone and closes the kiosk
- no leaked windows (teardown closes everything)

## Review focus

Inputs the spec implies that need pinning in tests:

- Idle timeout fires while the kiosk is mid-scan: the scan completes, the
  session ends, the kiosk stays.
- Phone request arrives during the logout transition: it is served or fails
  silent, never half-recorded (service layer locks already cover this).
- Kiosk exit attempted with the wrong password repeatedly: lockout counts it,
  same as today.
- Machine reboot with phone auto-start on: service starts before any sign-in
  (already true via `maybe_autostart_phone`; test pins it).
- Two admins: one signs out while the other signs in: services never flap.

## Sub-project order

A (this spec), then B Shifts, C Trust, D Printable timesheet, each with its
own spec, plan, implementation and review gate. Phase 3 background jobs
(auto-close timer, backup scheduler) plug into the Application-owned host from
this spec instead of the dashboard timer, so they run while the app is open
regardless of sign-in state.

## Conflicts

- The standing rule says one named phase at a time with a stop and wait. The

  sub-projects, each gated, instead of one large change.
